## 定义

**对象关系（Object Relationships）** 指面向对象设计中类与类之间的结构性关系，描述了对象之间的协作方式、生命周期归属、以及耦合程度。在 UML（统一建模语言）中，常见的三种核心关系是：**关联（Association）**、**组合（Composition）** 和 **依赖（Dependency）**，另有中间形态 **聚合（Aggregation）** 和 **泛化/继承（Generalization）**。

> 关联 → 聚合 → 组合 的耦合程度依次增强。组合关系下，"部分"随"整体"销毁；而关联只是引用，不负责生命周期。

## 三种关系总览

| 维度 | [[Dependency]]（依赖） | [[Association]]（关联） | [[Composition]]（组合） |
|------|------------------------|--------------------------|---------------------------|
| **关系类型** | uses-a（用一下） | has-a（持有） | part-of（是其一部分） |
| **作用范围** | 方法/函数级 | 类级（成员） | 类级（成员） |
| **持续性** | 临时（方法调用期间） | 长期 | 长期且同生共死 |
| **生命周期** | 互不干涉 | 双方独立 | 部分依赖整体 |
| **耦合强度** | 最弱 | 中 | 最强 |
| **C++ 体现** | 方法参数 / 局部变量 / 返回值 | 成员是裸指针 / 引用 / `weak_ptr` | 成员是值或 `unique_ptr` |
| **UML 符号** | 虚线箭头 ⇢ | 实线 — | 实心菱形 ◆— |
| **典型例子** | Car.refuel(GasStation) | 司机—汽车、学生—老师 | 汽车—引擎、人—心脏 |

## 判断口诀

> **状态进字段，操作走参数。**
> - 如果是这个对象"是什么"的一部分 → 成员
> - 如果是这个对象"做什么"时临时拿来用 → 参数

打开类定义，看成员变量列表：

```
├── 列表里没有 → 依赖（只在方法里见到）
├── 列表里有指针/引用 → 关联（不管生命周期）
└── 列表里有值/独占智能指针 → 组合（同生共死）
```

## 核心案例：Car 类同时呈现三种关系

```cpp
class Car {
private:
    Engine engine;    // 【组合】Engine 是 Car 的一部分（值成员）
    Driver* driver;   // 【关联】Car 长期记住一位司机，但不拥有他（裸指针）

public:
    // 【依赖】GasStation 只作为参数出现，方法结束就忘了
    void refuel(GasStation& station) {
        station.pump(50);
    }
};
```

- `Engine engine;` —— 类的字段，无法独立于 Car 存在 → **组合**
- `Driver* driver;` —— 类的字段（指针），但生命周期独立 → **关联**
- `void refuel(GasStation& station)` —— 仅出现在方法签名里，不是类的字段 → **依赖**

## 一句话判断法则

> **问自己一句话：如果"整体"被销毁了，"部分"还能不能继续存活并被别人使用？**
> - **能** → 关联（用指针/引用，不管生命周期）
> - **不能** → 组合（用值成员或 `unique_ptr`，负责其生命周期）

## 中间地带：聚合（Aggregation）

聚合介于关联与组合之间。球队解散后球员仍然存在，但语义上球员是球队的"组成部分"。

```cpp
class Team {
    std::vector<Player*> players;  // 聚合：球队"包含"球员，但球员可以独立存在
};
```

在 C++ 实现层面，聚合和关联几乎一致（都是非拥有指针）；区别在语义：聚合强调"整体—部分"，关联是更广义的"知道"。许多团队在实践中不严格区分。

## 设计原则

### 1. 最小可见原则——用最弱够用的关系

如果只需要一次性使用，就别提升为成员。每多知道一点就多耦合一分。关键问句：

> **这个东西是这个对象身份的一部分，还是只是它当前做这件事用一下？**

### 2. 依赖倒置 + [[Dependency_Injection|依赖注入]]

当确实需要做成员时，优先做两件事：
- **依赖抽象**（接口/基类），而非具体类
- **通过构造函数注入**，而不是在内部 `new`

### 3. [[Law_of_Demeter|迪米特法则]]

> **一个对象只跟它的"邻居"说话，不要跟"邻居的邻居"打交道。**

```cpp
// 不好：你只该认识 customer，不该穿透到 address 里去
customer.getAddress().getCity().getZipCode();

// 好：让 customer 自己暴露需要的接口
customer.getZipCode();
```

### 4. SRP（单一职责）的味道

- 一个类挂了 7、8 个成员对象 → "协作者过多"，可能是单一职责被破坏的信号
- 一个方法的参数列表特别长（>3-4 个） → 这些参数中可能隐藏着该被提为成员的协作者

### 5. 避免"过度保守"反模式

不要为了"低耦合"而把一切都写成方法参数：如果同一组对象总是一起出现在多个方法里，它们本质上就是这个类的"协作者"，应升级为成员。

## 实战决策流程

```
要不要把 X 做成成员变量？
│
├── 类的每个/多数方法都需要它？ ──→ 是，做成员
├── X 表示对象身份/状态的一部分？ ──→ 是，做成员
├── 跨方法调用需要保留 X 的状态？ ──→ 是，做成员
├── 想要外部可替换以便测试？ ──→ 通过构造函数注入（成员 + 接口）
│
├── 只在一两个方法里用一下？ ──→ 做参数
├── 每次调用都换不同的 X？ ──→ 做参数
└── 仅是一次性计算的输入？ ──→ 做参数
```

## 核心结论

设计的艺术是**诚实地表达关系，而不是机械地追求"低耦合"**：

- 如果两者都讲得通，选 **更弱** 的
- 但如果硬把"持有"扭曲为"使用"，就是把模型搞坏了
