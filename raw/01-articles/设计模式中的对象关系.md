# 设计模式中的对象关系：关联、组合与依赖

> 本文以 C++ 为例，系统梳理面向对象设计中三种核心结构性关系：**关联（Association）**、**组合（Composition）** 和 **依赖（Dependency）**，并讨论它们之间的边界与设计原则。

---

## 一、关联关系（Association）

### 1.1 定义与核心特征

关联是 UML 中描述类与类之间的一种结构性关系，表示一个类长期"知道"另一个类的存在（has-a 关系），通常通过成员变量（指针或引用）来实现。

**关联的核心特征：**

1. **长期持有**：不像依赖（Dependency）只是临时使用，关联是稳定的引用
2. **生命周期独立**：双方对象可以独立存在，互不负责创建和销毁
3. **方向性**：可以是单向或双向
4. **多重性**：可以是 1对1、1对多、多对多

> 注意区分：关联 → 聚合 → 组合 的耦合程度依次增强。组合关系下，"部分"随"整体"销毁；而关联只是引用，不负责生命周期。

### 1.2 C++ 代码示例：教师-学生（双向、一对多关联）

```cpp
#include <iostream>
#include <vector>
#include <string>
#include <algorithm>

class Teacher;  // 前向声明

class Student {
private:
    std::string name;
    Teacher* tutor;   // 关联：指向 Teacher 的指针（不拥有）

public:
    Student(const std::string& n) : name(n), tutor(nullptr) {}

    void setTutor(Teacher* t) { tutor = t; }
    const std::string& getName() const { return name; }
    Teacher* getTutor() const { return tutor; }
};

class Teacher {
private:
    std::string name;
    std::vector<Student*> students;  // 关联：持有多个 Student 的指针

public:
    Teacher(const std::string& n) : name(n) {}

    void addStudent(Student* s) {
        students.push_back(s);
        s->setTutor(this);   // 维护双向关联
    }

    void removeStudent(Student* s) {
        students.erase(
            std::remove(students.begin(), students.end(), s),
            students.end());
        s->setTutor(nullptr);
    }

    void showStudents() const {
        std::cout << name << " 的学生: ";
        for (auto* s : students) std::cout << s->getName() << " ";
        std::cout << "\n";
    }
};

int main() {
    // 注意：Teacher 和 Student 各自独立创建和销毁
    Student alice("Alice");
    Student bob("Bob");
    Teacher mrSmith("Mr. Smith");

    mrSmith.addStudent(&alice);
    mrSmith.addStudent(&bob);

    mrSmith.showStudents();
    std::cout << alice.getName() << " 的导师: "
              << alice.getTutor()->getName() << "\n";
    return 0;
}
```

### 1.3 关键点解析

| 设计要点 | 体现 |
| --- | --- |
| 结构稳定 | `Student::tutor` 和 `Teacher::students` 是成员变量，不是函数参数 |
| 不负责生命周期 | 使用裸指针，`Teacher` 析构时不会 `delete` 学生 |
| 双向导航 | 通过两端的成员变量，互相可以访问 |
| 多重性 | 一个 Teacher 对应多个 Student（vector），一个 Student 对应一个 Teacher |

> 如果使用 `std::unique_ptr<Student>` 持有学生，那就变成了 **组合** 关系——这是与关联最容易混淆的地方。区分的关键就在于：**谁负责管理生命周期**。

## 二、关联 vs 组合（Composition）

### 2.1 本质区别

二者最本质的区别是 **生命周期所有权**：

- **组合**：整体"拥有"部分，部分随整体而生、随整体而灭
- **关联**：只是"知道"对方，对方独立存活

### 2.2 对比表

| 维度 | 关联（Association） | 组合（Composition） |
| --- | --- | --- |
| 生命周期 | 双方独立 | 部分依赖整体，同生共死 |
| 所有权 | 无所有权 | 整体独占拥有部分 |
| 耦合强度 | 弱 | 最强 |
| 共享性 | 可被多个对象关联 | 一个部分只属于一个整体 |
| C++ 实现 | 裸指针 / 引用 / `weak_ptr` | 值成员 / `unique_ptr` |
| UML 符号 | 普通直线 | 实心菱形（指向整体侧） |
| 典型例子 | 司机—汽车、学生—老师 | 汽车—引擎、人—心脏 |

### 2.3 对比代码：同一个 Car 类，两种关系并存

```cpp
#include <iostream>
#include <string>

class Engine {
    int hp;
public:
    Engine(int h) : hp(h) { std::cout << "  Engine 诞生\n"; }
    ~Engine()              { std::cout << "  Engine 销毁\n"; }
};

class Driver {
    std::string name;
public:
    Driver(const std::string& n) : name(n) { std::cout << "Driver " << name << " 诞生\n"; }
    ~Driver()                               { std::cout << "Driver " << name << " 销毁\n"; }
};

class Car {
private:
    Engine engine;     // 【组合】值成员 —— Engine 是 Car 的一部分
    Driver* driver;    // 【关联】裸指针 —— Car 不拥有 Driver

public:
    Car(int hp) : engine(hp), driver(nullptr) {
        std::cout << "Car 诞生（同时构造 Engine）\n";
    }
    ~Car() {
        std::cout << "Car 销毁（同时析构 Engine）\n";
        // 注意：不 delete driver，因为不拥有它
    }
    void setDriver(Driver* d) { driver = d; }
};

int main() {
    Driver alice("Alice");          // Driver 先于 Car 出生
    {
        Car myCar(200);             // Car 出生 → Engine 自动出生
        myCar.setDriver(&alice);    // 建立关联
    }                               // Car 离开作用域 → Engine 一起死
    std::cout << "Car 已销毁，但 Alice 还活着\n";
}
```

**输出：**

```
Driver Alice 诞生
  Engine 诞生
Car 诞生（同时构造 Engine）
Car 销毁（同时析构 Engine）
  Engine 销毁              ← Engine 跟着 Car 一起死（组合）
Car 已销毁，但 Alice 还活着  ← Driver 不受影响（关联）
Driver Alice 销毁          ← Driver 独立销毁
```

### 2.4 一句话判断法则

> **问自己一句话：如果"整体"被销毁了，"部分"还能不能继续存活并被别人使用？**
>
> - **能** → 关联（用指针/引用，不管生命周期）
> - **不能** → 组合（用值成员或 `unique_ptr`，负责其生命周期）

### 2.5 中间地带：聚合（Aggregation）

实际上还有一种介于两者之间的关系叫 **聚合**：

```cpp
class Team {
    std::vector<Player*> players;  // 聚合：球队"包含"球员，但球员可以独立存在
};
```

球队解散后球员仍然存在，但语义上球员是球队的"组成部分"。

在 C++ 实现上，聚合和关联几乎一样（都是非拥有指针），区别只在概念语义层面：聚合强调"整体—部分"，关联是更广义的"知道"。所以很多团队在实践中不严格区分这两个。

## 三、依赖关系（Dependency）

### 3.1 定义

依赖是最弱的一种关系。它和关联/组合最本质的区别是：**依赖是"用一下"，关联/组合是"持有住"**。

- **关联/组合**：A 的结构里就有 B（成员变量），是一种长期的、结构性的关系
- **依赖**：A 只是在某个方法执行时临时用一下 B（参数、局部变量、返回值），用完就走

UML 中也专门用虚线箭头表示依赖，以示其"轻量、临时"。

### 3.2 三者完整对比

| 维度 | 依赖 Dependency | 关联 Association | 组合 Composition |
| --- | --- | --- | --- |
| 关系类型 | uses-a（用一下） | has-a（持有） | part-of（是其一部分） |
| 作用范围 | 方法/函数级 | 类级（成员） | 类级（成员） |
| 持续性 | 临时（方法调用期间） | 长期 | 长期且同生共死 |
| 生命周期 | 互不干涉 | 双方独立 | 部分依赖整体 |
| 耦合强度 | 最弱 | 中 | 最强 |
| C++ 体现 | 方法参数 / 局部变量 / 返回值 | 成员是裸指针/引用 | 成员是值或 `unique_ptr` |
| UML 符号 | 虚线箭头 ⇢ | 实线 — | 实心菱形 ◆— |

### 3.3 一段代码同时展示三者

让我们扩展之前的 Car 例子，让它同时拥有三种关系：

```cpp
#include <iostream>
#include <string>

class Engine {
public:
    Engine()  { std::cout << "  Engine 诞生\n"; }
    ~Engine() { std::cout << "  Engine 销毁\n"; }
};

class Driver {
    std::string name;
public:
    Driver(const std::string& n) : name(n) {}
    const std::string& getName() const { return name; }
};

// 加油站：Car 在 refuel() 时才会用到它
class GasStation {
public:
    void pump(int liters) {
        std::cout << "加油站为车加了 " << liters << " 升油\n";
    }
};

class Car {
private:
    Engine engine;    // 【组合】Engine 是 Car 的一部分
    Driver* driver;   // 【关联】Car 长期记住一位司机，但不拥有他

public:
    Car() : driver(nullptr) { std::cout << "Car 诞生\n"; }
    ~Car()                  { std::cout << "Car 销毁\n"; }

    void setDriver(Driver* d) { driver = d; }

    // 【依赖】GasStation 只作为参数出现，方法结束就忘了
    void refuel(GasStation& station) {
        station.pump(50);
    }
};

int main() {
    Driver alice("Alice");
    Car car;
    car.setDriver(&alice);          // 建立关联

    GasStation station;             // GasStation 独立存在
    car.refuel(station);            // 临时依赖：仅在此调用期间用一下
}                                   // Car 销毁 → Engine 死；Driver、GasStation 都还活着
```

**关键观察：**

- `Engine engine;` —— 类的字段，无法独立于 Car 存在 → **组合**
- `Driver* driver;` —— 类的字段（指针），但生命周期独立 → **关联**
- `void refuel(GasStation& station)` —— 仅出现在方法签名里，不是类的字段 → **依赖**

### 3.4 容易混淆的边界

#### 边界一：把依赖"升级"成关联

```cpp
// 依赖
class OrderService {
    void process(Logger& log) { log.info("..."); }
};

// 关联（把 Logger 提升为成员）
class OrderService {
    Logger* log;
public:
    OrderService(Logger* l) : log(l) {}
    void process() { log->info("..."); }
};
```

构造函数注入往往把"依赖"升级为"关联"——一旦把对方存为成员，关系就从临时变成长期了。

#### 边界二：短暂存在但被存住，算什么？

判断标准不是"用了多久"，而是 **"是不是类的结构组成部分"**。

哪怕方法里只调用一次，只要存为成员，就是关联；反之，哪怕调用持续好几小时，只要它只是个参数，就是依赖。

### 3.5 一句话总结判断法则

打开类定义，看成员变量列表：

```
├── 列表里没有 → 依赖（只在方法里见到）
├── 列表里有指针/引用 → 关联（不管生命周期）
└── 列表里有值/独占智能指针 → 组合（同生共死）
```

## 四、设计原则与取舍

### 4.1 核心结论：不是越弱越好

直觉上"依赖比关联耦合更弱，所以依赖更好"，这是误解。真正的原则是：

> **让代码结构反映真实的语义关系。** 强行把"持有"关系扭曲成"使用"关系，会让代码变得难用且不诚实。

举个反例，如果一个 `Car` 类把 `Engine` 也变成方法参数：

```cpp
void Car::accelerate(Engine& e) { e.ignite(); }    // 别扭
void Car::brake(Engine& e)      { e.cutFuel(); }
void Car::idle(Engine& e)       { e.maintain(); }
```

每次都传同一个 engine 是冗余且违反直觉的——Car 显然就是有 Engine 的，把它降级成依赖是对模型的扭曲。

### 4.2 何时用关联（成员）、何时用依赖（参数）

| 场景 | 推荐 | 理由 |
| --- | --- | --- |
| 几乎每个方法都要用 | 成员（关联） | 避免重复传参 |
| 跨方法保持状态/身份 | 成员（关联） | 它属于对象的"自我"一部分 |
| 整个对象生命周期内引用同一个 | 成员（关联） | 体现长期协作 |
| 仅在某一两个方法中使用 | 参数（依赖） | 不污染类的结构 |
| 每次调用传入的不同 | 参数（依赖） | 本来就该外部决定 |
| 仅用于一次性的转换/计算 | 参数 / 返回值 | 临时性强 |

### 4.3 几条核心设计原则

#### 原则 1：最小可见原则——用最弱够用的关系

如果只需要一次性使用，就别提升为成员。写代码本质是在传递"知识"，每多知道一点就多耦合一分。

关键问句：

> **这个东西是这个对象身份的一部分，还是只是它当前做这件事用一下？**

#### 原则 2：依赖倒置 + 依赖注入

当确实需要做成员时，优先做两件事：

- **依赖抽象**（接口/基类），而非具体类
- **通过构造函数注入**，而不是在内部 `new`

```cpp
class Logger { public: virtual void info(const std::string&) = 0; };

class ReportGenerator {
    Logger* log;  // 依赖抽象，而非 ConsoleLogger 具体类
public:
    ReportGenerator(Logger* l) : log(l) {}  // 注入，而不是内部 new
};
```

这让"关联"在结构上虽然存在，但耦合的是接口而不是实现，**可替换、可测试**。

#### 原则 3：迪米特法则（Law of Demeter）

> **一个对象只跟它的"邻居"说话，不要跟"邻居的邻居"打交道。**

```cpp
// 不好：你只该认识 customer，不该穿透到 address 里去
customer.getAddress().getCity().getZipCode();

// 好：让 customer 自己暴露需要的接口
customer.getZipCode();
```

成员是结构性的耦合，如果你的成员的成员的成员都得知道，这条链就太长了——拆分或加聚合方法。

#### 原则 4：SRP——成员变量数量也是一个味道

一个类如果挂了 7、8 个成员对象，通常说明它"协作者过多"，可能是单一职责被破坏的信号——考虑拆分，或抽出参数对象/协作者集合。

反过来，如果一个方法的参数列表特别长（超过 3-4 个），这些参数中往往隐藏着该被提为成员的协作者。

#### 原则 5：避免"过度保守"反模式

不要为了"低耦合"而把一切都写成方法参数：

```cpp
// 反模式：洁癖式纯函数风格
class BadDesign {
public:
    void method1(Db& db, Log& log, Config& cfg, User& u);
    void method2(Db& db, Log& log, Config& cfg);
    void method3(Db& db, Log& log);
    // 每个方法都在传同样的东西...
};
```

如果同一组对象总是一起出现在多个方法里，它们本质上就是这个类的"协作者"，该升级为成员。

### 4.4 实战决策流程

```
要不要把 X 做成成员变量？
│
├── 类的每个/多数方法都需要它？──→ 是，做成员
├── X 表示对象身份/状态的一部分？──→ 是，做成员
├── 跨方法调用需要保留 X 的状态？──→ 是，做成员
├── 想要外部可替换以便测试？──→ 通过构造函数注入（成员 + 接口）
│
├── 只在一两个方法里用一下？──→ 做参数
├── 每次调用都换不同的 X？──→ 做参数
└── 仅是一次性计算的输入？──→ 做参数
```

### 4.5 一个浓缩的判断口诀

> **状态进字段，操作走参数。**
>
> - 如果是这个对象"是什么"的一部分 → 成员
> - 如果是这个对象"做什么"时临时拿来用 → 参数

**举例对照：**

```cpp
class FileTransferTask {
    std::string sourceUrl;     // 状态（任务的一部分）→ 成员
    std::string targetPath;    // 状态 → 成员
    Logger* log;               // 协作者（每步都要记录）→ 成员（注入）

public:
    // 操作参数（每次重试不同）
    void execute(int retryCount, ProgressReporter& progress);
};
```

`sourceUrl` 是这个 task "是什么"；`retryCount` 是这次 "怎么执行"——分得很清楚。

## 五、总结

关联和依赖没有谁好谁坏，关键是 **"匹配现实 + 用最弱够用的"**：

- 如果两者都讲得通，选 **更弱** 的
- 但如果硬把"持有"扭曲为"使用"，就是把模型搞坏了

**设计的艺术是诚实地表达关系，而不是机械地追求"低耦合"。**

继承关系是另一个维度，下一步可以继续探讨 **继承 vs 组合**——这是面向对象设计中最经典的取舍。
